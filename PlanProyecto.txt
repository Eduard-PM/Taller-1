Análisis de Funcionalidades y Flujos de Usuario
El sistema propuesto se centra en la detección de caídas de un usuario a través de su teléfono móvil, con el objetivo de notificar a un contacto de emergencia en caso de que el usuario no pueda responder tras un posible incidente.
Condiciones Previas Fundamentales:
El usuario debe haber guardado previamente un número de teléfono de emergencia dentro de la aplicación.
Este número será el destinatario de la llamada automática en caso de una emergencia confirmada.
Desglose de Funcionalidades por Historia de Usuario (HU):
HU 1: Detección de Caídas
Funcionalidad Principal: El sistema monitorea de forma constante los sensores de movimiento (acelerómetro) del dispositivo móvil para identificar patrones que sugieran una caída.
Reglas de Negocio:
La detección se activa cuando los datos del acelerómetro superan un umbral preestablecido que indica un movimiento brusco y anómalo.
Para evitar notificaciones repetitivas, el sistema implementa un periodo de enfriamiento después de generar una alerta, impidiendo que se active otra inmediatamente.
Criterios de Aceptación:
El sistema debe ser capaz de identificar y registrar al menos un evento de caída real.
Durante actividades cotidianas como caminar o sentarse, la aplicación no debe generar falsas alarmas.
Una vez detectada una posible caída, el sistema debe pasar la señal para activar el flujo de confirmación (descrito en HU 2).
HU 2: Aviso de Confirmación al Usuario
Funcionalidad Principal: Tras detectar una posible caída, la aplicación presenta una interfaz de confirmación para que el usuario verifique si se encuentra bien.
Reglas de Negocio:
Una notificación o pantalla de alerta debe aparecer de forma inmediata, incluso si el dispositivo está bloqueado.
Esta alerta contiene un botón claramente visible con la etiqueta "Estoy bien".
Si el usuario no interactúa con la alerta en un plazo de 10 segundos, el sistema asume que necesita ayuda y procede con el siguiente paso (HU 3 y HU 4).
Criterios de Aceptación:
La pantalla de aviso se muestra correctamente tras una detección.
Pulsar el botón "Estoy bien" dentro del tiempo establecido cancela la alerta y el flujo de emergencia.
Si transcurren los 10 segundos sin respuesta, el sistema avanza automáticamente a la fase de llamada de emergencia.
HU 3: Gestión del Número de Emergencia
Funcionalidad Principal: Permitir al usuario configurar y actualizar el contacto de emergencia al que se llamará en caso de un incidente.
Reglas de Negocio:
El sistema debe validar que el número introducido sea un formato de teléfono válido, rechazando entradas con letras u otros caracteres no permitidos.
El número guardado debe persistir en la memoria de la aplicación, incluso si esta se cierra y se vuelve a abrir.
Este será el número utilizado exclusivamente para la llamada automática de emergencia (HU 4).
Criterios de Aceptación:
El usuario tiene acceso a una sección para introducir y guardar su número de emergencia.
Existe la opción de editar este número en cualquier momento.
El número guardado es efectivamente el que se utiliza cuando se activa la llamada automática.
HU 4: Llamada Automática de Emergencia
Funcionalidad Principal: Realizar una llamada telefónica automática al número de emergencia configurado si el usuario no responde al aviso de confirmación.
Reglas de Negocio:
La llamada se inicia únicamente si no se ha pulsado el botón "Estoy bien" en el tiempo estipulado.
La acción de llamar finaliza el flujo de emergencia dentro de la aplicación.
Criterios de Aceptación:
La llamada se inicia en menos de 5 segundos después de que expira el tiempo de confirmación.
La llamada se dirige correctamente al número de emergencia previamente guardado por el usuario.
Si el número no es válido o hay un error al intentar llamar, la aplicación debe mostrar un mensaje de error claro sin bloquearse o cerrarse inesperadamente.
HU 5: Historial de Incidentes
Funcionalidad Principal: Proporcionar un registro detallado de todos los eventos detectados, tanto emergencias reales como falsas alarmas.
Reglas de Negocio:
Cada vez que el acelerómetro detecta un evento que supera el umbral, se crea una nueva entrada en el historial.
Cada registro debe incluir: fecha, hora, tipo de movimiento, ubicación GPS (si está disponible), duración del incidente, la acción final (cancelado por el usuario o llamada realizada) y el contacto notificado.
Criterios de Aceptación:
El historial se presenta en orden cronológico descendente (los eventos más recientes primero).
Se utilizan iconos o indicadores visuales para diferenciar claramente entre una falsa alarma (cancelada) y una emergencia real (llamada efectuada).
Flujo del Proceso (Basado en el Diagrama)
Activación y Monitoreo: La aplicación se encuentra en un estado de monitoreo constante del acelerómetro.
Detección de Caída:
¿La aceleración supera el límite establecido?
No: El sistema continúa monitoreando sin interrupción.
Sí: Se activa el protocolo de emergencia.
Confirmación del Usuario:
Se muestra en pantalla un cuadro de diálogo con la pregunta "¿Estás bien?" y un botón de confirmación.
El sistema inicia una cuenta regresiva de 10 segundos.
Decisión del Usuario:
¿El usuario presiona "Estoy bien" dentro de los 10 segundos?
Sí: El flujo de emergencia se cancela y la aplicación vuelve al estado de monitoreo. El evento se podría registrar como "falsa alarma" en el historial (HU 5).
No: El sistema interpreta la falta de respuesta como una emergencia real.
Acción de Emergencia:
El sistema procede a marcar automáticamente al número de emergencia que el usuario ha guardado previamente (HU 3 y HU 4).
Una vez realizada la llamada, el flujo concluye. El evento se registra como "emergencia real" en el historial (HU 5).
